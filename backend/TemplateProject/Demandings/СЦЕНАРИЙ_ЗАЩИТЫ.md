## Слайд 2: Актуальность проблемы

**Заголовок:** Почему эта система важна?

**Ключевые моменты:**

- **Растущий объем встреч в компаниях** — с развитием удалённой работы количество онлайн-встреч выросло в 3-5 раз. Сложно координировать разные часовые пояса и расписания.

- **Потеря времени на организацию** — сотрудники тратят по 2-3 часа в день на согласование времени встреч через переписку в мессенджерах.

- **Конфликты по времени** — люди забывают о назначенных встречах или получают приглашения на пересекающиеся события.

- **Отсутствие единого решения** — компании используют разные инструменты (Google Calendar, Outlook, Telegram), что создаёт путаницу.

**Текст для ведущего:**

В современном мире, особенно с развитием удалённой работы, координация встреч стала одной из главных проблем в командах. Люди работают в разных часовых поясах, у каждого свой календарь и свои обязательства. Meeting Management System решает эту проблему, предоставляя единую платформу для планирования, координации и отслеживания встреч в реальном времени.

## Слайд 3: Цели и задачи проекта

**Заголовок:** Что мы хотим достичь?

**Основная цель:**
Разработать интуитивную, безопасную и масштабируемую систему для управления встречами, которая упростит планирование и координацию времени в командах любого размера.

**Основные задачи:**

1. **Аутентификация и управление пользователями** — безопасная регистрация, вход, управление ролями (User, Organizer, Admin)

2. **CRUD встреч** — полноценное управление встречами: создание, редактирование, удаление со всеми деталями (формат, время, место, участники)

3. **Проверка занятости** — система должна предотвращать наложение встреч, автоматически проверяя календари участников

4. **Управление участниками** — приглашение пользователей, сбор ответов (принял/отклонил), отслеживание обязательных участников

5. **Работа с файлами** — возможность прикреплять документы, презентации и материалы к встречам

6. **История и архив** — сохранение информации о произошедших встречах для аналитики

**Текст для ведущего:**

Мы поставили перед собой амбициозные, но достижимые задачи. Система должна не просто хранить информацию о встречах, но и активно помогать пользователям избежать конфликтов, управлять сложными сценариями с обязательными участниками и предоставлять полную историю всех мероприятий для анализа.

## Слайд 4: Архитектура системы

**Заголовок:** Как работает система?

**Диаграмма (описание для слайда):**

```
┌─────────────────────────┐
│     React + TypeScript  │  ← Фронтенд (UI/UX)
│   (Single Page App)     │
└────────────┬────────────┘
             │ HTTP/REST API
             │
┌────────────▼────────────┐
│   C# / .NET 9 Backend   │
│  - MediatR (CQRS)       │
│  - Entity Framework      │
│  - JWT Authentication   │
│  - PostgreSQL Database  │
└────────────┬────────────┘
             │
┌────────────▼────────────┐
│   PostgreSQL Database   │
│  (Таблицы встреч,       │
│   участников, файлов)   │
└─────────────────────────┘
```

**Компоненты:**

- **Frontend:** React приложение на TypeScript с компонентами для управления встречами, календарём, участниками
- **Backend:** REST API на C# и .NET 9 с использованием CQRS паттерна через MediatR
- **Database:** PostgreSQL для надёжного хранения данных с поддержкой сложных запросов

**Текст для ведущего:**

Система построена по классической трёхуровневой архитектуре. На фронте пользователи работают с интерфейсом React, который красивый и отзывчивый. Фронт общается с backend через REST API. Backend обрабатывает бизнес-логику, проверяет права доступа и работает с базой данных PostgreSQL. Все компоненты хорошо разделены и независимы, что позволяет им развиваться отдельно друг от друга.

## Слайд 9: Технические особенности и инновации

**Заголовок:** Что делает нашу систему особенной?

**Инновационные подходы:**

1. **CQRS паттерн (Command Query Responsibility Segregation)**
   - Команды отделены от запросов для лучшей организации кода
   - Легче тестировать и масштабировать
   - Каждая операция явно определена как Command или Query

2. **Проверка занятости в реальном времени**
   - Алгоритм проверяет временные пересечения: `startTime < existingEnd AND endTime > existingStart`
   - Исключает встречи со статусом "Отменена" и "Черновик"
   - Показывает конкретные конфликты пользователю

3. **Soft Delete вместо физического удаления**
   - Встречи никогда не удаляются, а помечаются как удалённые
   - Сохраняется полная история для аудита
   - Легче восстановить данные при случайном удалении

4. **Управление ролями на основе коллекции, а не первого элемента**
   - Одному пользователю может быть несколько ролей
   - Система проверяет всю коллекцию ролей, а не только первую
   - Большая гибкость в управлении правами доступа

5. **Индексы в базе данных для производительности**
   - Оптимизированы запросы по meetingId, userId, date, status
   - Составной уникальный индекс на (meetingId, userId)
   - Система быстро работает даже с большим объёмом данных

**Текст для ведущего:**

Мы использовали несколько продвинутых подходов, которые делают систему надёжной и производительной. CQRS паттерн обеспечивает чистую архитектуру. Soft delete позволяет нам никогда не терять данные. Умный алгоритм проверки занятости работает в реальном времени без задержек. И всё это работает быстро благодаря оптимизированным индексам в базе данных.

## Дополнительная информация для Q&A

### Вопрос: Насколько система безопасна?

**Ответ:** Очень. Мы используем JWT токены для аутентификации, что предотвращает несанкционированный доступ. Все пароли хешируются с использованием bcrypt. У каждого пользователя есть роль, которая определяет, что он может делать. Система проверяет права на каждое действие. Данные не удаляются физически (soft delete), поэтому есть полная история всех операций, что позволяет провести аудит при необходимости.

### Вопрос: Сколько одновременных пользователей может поддерживать система?

**Ответ:** Благодаря использованию .NET 9 и PostgreSQL система может легко масштабироваться. На одном сервере она может обслуживать тысячи одновременных пользователей. При необходимости можно добавить кэширование (Redis), балансировку нагрузки и репликацию БД. Сейчас система оптимизирована под средние компании, но архитектура позволяет масштабировать до корпоративных масштабов.

### Вопрос: Как система работает с разными часовыми поясами?

**Ответ:** Все времена в системе хранятся в UTC (Coordinated Universal Time) в базе данных. При отправке на фронтенд мы преобразуем время в локальный часовой пояс пользователя. Фронтенд используется информацию из браузера пользователя. Таким образом, каждый видит встречи в своём часовом поясе, но сравнение и проверка конфликтов происходит в единой системе координат UTC.

### Вопрос: Что происходит, если пользователь удалит встречу?

**Ответ:** Встреча не удаляется из БД, а помечается как удалённая (soft delete). Записываются: время удаления и ID пользователя, который выполнил удаление. Встреча больше не видна обычным пользователям, но администратор может видеть удалённые встречи и при необходимости восстановить. Это обеспечивает безопасность данных и полную аудируемость.

### Вопрос: Как быстро работает проверка занятости?

**Ответ:** Очень быстро — обычно меньше 100 миллисекунд. Это возможно благодаря индексам на таблице встреч (по userId, date, status). Система не проверяет все встречи подряд, а использует оптимизированные SQL запросы для выборки только релевантных встреч. Даже при большом объёме данных проверка остаётся практически мгновенной.

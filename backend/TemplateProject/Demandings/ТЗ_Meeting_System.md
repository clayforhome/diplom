## 1. Авторизация и регистрация пользователей

Назначение: обеспечить идентификацию пользователей и контроль доступа к системе.

### 1.1 Функциональные требования

- Регистрация через форму (email + password + username)
- Вход по email и паролю
- Выход из системы (логаут / инвалидация токена)
- Смена пароля авторизованным пользователем
- Восстановление пароля (reset по email)
- Деактивация аккаунта администратором

### 1.2 Схема сущности User

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| id | UUID / BIGINT | да | Первичный ключ |
| username | VARCHAR(100) | да | Отображаемое имя |
| email | VARCHAR(255) | да | Уникальный, используется для входа |
| passwordHash | VARCHAR | да | Хеш пароля (bcrypt/argon2) |
| role | ENUM | да | USER │ ORGANIZER │ ADMIN |
| status | ENUM | да | ACTIVE │ DEACTIVATED |
| createdAt | TIMESTAMP | да | Дата регистрации |
| updatedAt | TIMESTAMP | да | Дата последнего обновления |

> ⚠ Пароль хранится исключительно в виде хеша. Никогда не возвращать `passwordHash` в API-ответах.

### 1.3 Бизнес-правила

- Email должен быть уникальным в системе
- Деактивированный пользователь не может войти в систему
- Только ADMIN может изменять статус других пользователей

## 2. Роли и права доступа

Назначение: разграничение прав для выполнения действий в системе. Система использует три роли с иерархическим наследованием прав.

| Действие | USER | ORGANIZER | ADMIN |
|----------|------|-----------|-------|
| Просмотр своих встреч | ✓ | ✓ | ✓ |
| Просмотр всех встреч системы | ✗ | ✗ | ✓ |
| Ответ на приглашения | ✓ | ✓ | ✓ |
| Создание встречи | ✗ | ✓ | ✓ |
| Редактирование встречи | ✗ | ✓ (своей) | ✓ |
| Удаление встречи | ✗ | ✓ (своей) | ✓ |
| Приглашение участников | ✗ | ✓ | ✓ |
| Перенос / отмена встречи | ✗ | ✓ (своей) | ✓ |
| Управление пользователями | ✗ | ✗ | ✓ |
| Изменение ролей | ✗ | ✗ | ✓ |
| Удаление тестовых данных | ✗ | ✗ | ✓ |

> ⚠ Роль хранится в таблице `User`. При необходимости расширения — вынести в отдельную таблицу `Role` с таблицей связи `user_roles`.

## 3. Управление встречами (CRUD)

Назначение: основной жизненный цикл мероприятия. Это центральная сущность системы.

### 3.1 Схема сущности Meeting

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| id | UUID / BIGINT | да | Первичный ключ |
| title | VARCHAR(255) | да | Название встречи |
| description | TEXT | нет | Описание / повестка |
| date | DATE | да | Дата проведения |
| startTime | TIME / TIMESTAMP | да | Время начала |
| endTime | TIME / TIMESTAMP | да | Время окончания |
| organizerId | FK → User.id | да | Организатор встречи |
| format | ENUM | да | OFFLINE │ ONLINE │ HYBRID │ PHONE |
| status | ENUM | да | См. раздел 5 |
| location | VARCHAR(500) | условно | Обязателен для OFFLINE и HYBRID |
| meetingLink | VARCHAR(500) | условно | Обязателен для ONLINE и HYBRID |
| contactInfo | VARCHAR(255) | условно | Обязателен для PHONE |
| isDeleted | BOOLEAN | да | Soft delete флаг, default: false |
| deletedAt | TIMESTAMP | нет | Время удаления |
| deletedBy | FK → User.id | нет | Кто выполнил удаление |
| createdAt | TIMESTAMP | да | Дата создания |
| updatedAt | TIMESTAMP | да | Дата последнего обновления |

### 3.2 Создание встречи

- Доступно только ORGANIZER и ADMIN
- Обязательные поля: `title`, `date`, `startTime`, `endTime`, `organizerId`, `format`, `status`
- Валидация: `startTime < endTime` (иначе — ошибка 400)
- Валидация по формату: см. раздел 4
- При создании `status` может быть `DRAFT` или `SCHEDULED`
- Встреча в статусе `DRAFT` не видна участникам

### 3.3 Редактирование встречи

- Можно изменять любые поля встречи
- При изменении даты или времени — автоматически отправить уведомления всем участникам
- При изменении времени статус автоматически меняется на `RESCHEDULED`
- Организатор видит сводную статистику ответов участников

### 3.4 Удаление встречи (Soft Delete)

- Физическое удаление из БД **ЗАПРЕЩЕНО**
- При удалении устанавливать: `isDeleted = true`, `deletedAt = now()`, `deletedBy = currentUserId`
- Все запросы по умолчанию фильтруют `isDeleted = false`

> ✓ Добавить глобальный фильтр/middleware на уровне ORM для автоматической фильтрации удалённых записей.

## 4. Форматы встреч и валидация

Тип встречи определяет, какие поля являются обязательными. Валидация должна происходить на уровне бизнес-логики (сервис), а не только на уровне БД.

| Формат | Обязательные поля | Описание |
|--------|-------------------|----------|
| OFFLINE | location (адрес + кабинет) | Очная встреча — требует физический адрес |
| ONLINE | meetingLink (URL платформы) | Онлайн — требует ссылку на конференцию |
| HYBRID | location + meetingLink | Смешанный — оба поля обязательны |
| PHONE | contactInfo (номер/мессенджер) | Телефонный звонок — требует контактные данные |

> ⚠ Валидировать наличие нужных полей перед сохранением. Возвращать понятное сообщение об ошибке при отсутствии обязательного поля формата.

## 5. Статусы встречи (State Machine)

Назначение: отражать текущее состояние мероприятия. Переходы между статусами должны контролироваться на уровне бизнес-логики.

| Статус | Видна участникам | Описание и условия перехода |
|--------|------------------|-----------------------------|
| DRAFT | Нет | Черновик. Начальный статус при создании. Не виден участникам до публикации. |
| SCHEDULED | Да | Запланирована. Встреча опубликована и ожидает подтверждений. |
| AWAITING_CONFIRMATION | Да | Ожидает подтверждения от обязательных участников. |
| CONFIRMED | Да | Подтверждена. Все обязательные участники приняли приглашение. |
| RESCHEDULED | Да | Перенесена. Устанавливается автоматически при изменении даты/времени. |
| CANCELLED | Да | Отменена. Финальный статус, дальнейшие изменения невозможны. |
| COMPLETED | Да | Завершена. Устанавливается автоматически после окончания встречи (endTime прошёл). |

> ✓ Реализовать scheduled job / cron для автоматического перевода встреч в статус `COMPLETED` после окончания времени.

## 6. Приглашение участников и управление

Назначение: добавление пользователей во встречу и сбор обратной связи по участию.

### 6.1 Схема сущности MeetingParticipant

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| id | UUID / BIGINT | да | Первичный ключ |
| meetingId | FK → Meeting.id | да | Ссылка на встречу |
| userId | FK → User.id | да | Ссылка на пользователя |
| invitationStatus | ENUM | да | PENDING │ ACCEPTED │ DECLINED |
| isRequired | BOOLEAN | да | Обязательный участник (не может отказаться) |
| invitedAt | TIMESTAMP | да | Время отправки приглашения |
| responseAt | TIMESTAMP | нет | Время ответа на приглашение |
| comment | TEXT | нет | Комментарий участника при ответе |

### 6.2 Правила приглашения

- Приглашать можно одного или нескольких пользователей одновременно
- Дубликаты участников в одной встрече недопустимы (уникальный индекс `meetingId + userId`)
- При приглашении статус автоматически устанавливается в `PENDING`
- Организатор видит: кто принял, кто отклонил, кто не ответил, и комментарии

### 6.3 Ответ на приглашение

- Доступные статусы ответа: `ACCEPTED`, `DECLINED`, `PENDING` (ещё не решил)
- Обязательный участник (`isRequired = true`) — ему **ЗАПРЕЩЕНО** устанавливать статус `DECLINED`
- При ответе фиксировать `responseAt = now()`
- Комментарий при ответе — опциональное поле

> ⚠ Если все обязательные участники ответили `ACCEPTED`, автоматически перевести встречу в статус `CONFIRMED`.

## 7. Проверка занятости (Conflict Check)

Назначение: предотвратить наложение встреч у участников. Это критически важный эндпоинт — реализовать в приоритете.

### 7.1 Логика проверки

- Сравнивать временные интервалы в календарях всех приглашаемых участников
- Конфликт = пересечение интервалов: `newStart < existingEnd AND newEnd > existingStart`
- Проверка выполняется для каждого участника отдельно
- Не учитывать встречи со статусом `CANCELLED` и `DRAFT` при проверке конфликтов

### 7.2 Формат ответа

- Список участников, у которых есть конфликт (`userId`, `username`, конфликтующие встречи)
- Конкретные временные интервалы конфликтов
- Предупреждение организатору с предложением выбрать другое время
- Проверка **НЕ блокирует** создание встречи — это предупреждение, не ошибка

> ✓ Реализовать как отдельный эндпоинт: `POST /api/meetings/check-availability` с телом `{ participantIds[], date, startTime, endTime }`

## 8. Календарь встреч

Назначение: визуализация расписания пользователя и фильтрация встреч по временному диапазону.

### 8.1 Режимы отображения

- По дням: все встречи за конкретную дату
- По неделям: встречи в диапазоне 7 дней
- По месяцам: все встречи за месяц

### 8.2 Данные в ответе

- Дата и время начала/окончания
- Длительность встречи
- Статус встречи
- Список участников (краткий)
- Формат встречи

### 8.3 Фильтры

- По статусу (`SCHEDULED`, `CONFIRMED`, и т.д.)
- По участнику (`userId`)
- По формату (`ONLINE`, `OFFLINE`, `HYBRID`, `PHONE`)
- Будущие / прошедшие
- Мои встречи / все встречи (для ADMIN)

## 9. Поиск и фильтрация

Назначение: быстрый доступ к нужным встречам через текстовый поиск и комбинацию фильтров.

### 9.1 Параметры поиска

- По названию (`title`) — частичное совпадение, case-insensitive
- По дате (`date`) — точное совпадение или диапазон
- По участнику (`userId` / `username`)
- По организатору (`organizerId`)

### 9.2 Фильтры

- Будущие / прошедшие встречи
- Мои встречи / все встречи
- По статусу (один или несколько)
- По формату (один или несколько)
- Встречи, где пользователь является обязательным участником (`isRequired = true`)

> ✓ Реализовать единый эндпоинт `GET /api/meetings` с query-параметрами для всех фильтров. Использовать пагинацию (`page`, `limit`).

## 10. История встреч

Назначение: доступ к архивным данным — завершённым, отменённым и перенесённым встречам.

- Включает встречи со статусами: `COMPLETED`, `CANCELLED`, `RESCHEDULED`
- Хранить полный состав участников и их финальные статусы ответа
- Хранить финальный статус встречи на момент завершения
- Доступна пагинация и сортировка (по дате, статусу)

## 11. Прикрепление файлов

Назначение: обеспечить участников необходимыми материалами (повестки, презентации, отчёты).

### 11.1 Схема сущности File

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| id | UUID / BIGINT | да | Первичный ключ |
| meetingId | FK → Meeting.id | да | Привязка к встрече |
| fileName | VARCHAR(255) | да | Оригинальное имя файла |
| filePath | VARCHAR(500) | да | Путь в хранилище (S3, диск) |
| fileType | VARCHAR(100) | да | MIME-тип файла |
| uploadedBy | FK → User.id | да | Кто загрузил |
| uploadedAt | TIMESTAMP | да | Время загрузки |

### 11.2 Поддерживаемые типы файлов

## 14. Нефункциональные требования

### 14.1 Безопасность

- JWT для аутентификации (access token + refresh token)
- Хеширование паролей: bcrypt (cost factor ≥ 12) или argon2
- Валидация всех входящих данных на уровне контроллера
- Rate limiting на эндпоинтах авторизации
- Не возвращать `passwordHash` в ответах API

### 14.2 Надёжность и производительность

- Индексы: `meetingId`, `userId`, `date`, `status` в таблице `meetings`
- Составной уникальный индекс: `(meetingId, userId)` в `meeting_participants`
- Пагинация на всех списочных эндпоинтах (`page`, `limit`, по умолчанию `limit=20`)
- Мягкое удаление (soft delete) — физического удаления встреч нет

### 14.3 Уведомления (минимальный контракт)

- При изменении встречи — уведомить всех участников (email или in-app)
- При создании приглашения — уведомить приглашённых
- Реализация механизма уведомлений — на усмотрение агента (очередь или прямой вызов)
